## 1. 最重要要件

### R-1. Googleスプレッドシートのコピーであること

画面と操作は Googleスプレッドシートを再現する。「どう動くのが正しいか」に迷ったときは、Googleスプレッドシートの挙動を正解とする。

- キー操作は Googleスプレッドシートと同じにする（例: Ctrl+C / Ctrl+V / Ctrl+Z、Ctrl+D で下方向へのコピー、Ctrl+Shift+V で値のみ貼り付け、Ctrl+/ でショートカット一覧）
- マウス操作も同じにする（例: ドラッグで範囲選択、フィルハンドルのドラッグによる連続データの入力、列ヘッダーをクリックして列全体を選択、境界ドラッグで列幅を変更）
- 数式は Googleスプレッドシートと同じ関数・演算子で書ける（セル番地の代わりに列名を書く）
- Googleスプレッドシートとの間で、範囲のコピーと貼り付けがそのまま往復できる

### R-2. リソースは YAML または JSON であること

画面上のシートの中身は、そのまま YAML または JSON のファイル（リソース）として保存する。データベースや独自のバイナリ形式は使わない。

- 1 シート＝1 ファイル
- YAML と JSON のどちらで保存するかは、プロジェクトごとに選ぶ
- ファイルは人が読めて、差分が小さい形で書き出す（1 セルを変えたら、ファイルの差分もおおむね 1 行）

### R-1 と R-2 の関係（具体例）

画面（Googleスプレッドシートと同じ見た目）:

| | A: id | B: name（名前） | C: rarity（レアリティ） | D: hp（HP） |
|---|---|---|---|---|
| 1 | 1 | 勇者アルス | SSR | 1200 |
| 2 | 2 | 魔法使いリナ | SR | 800 🟥（メモ: 次回調整予定） |

YAML で保存した場合（`tables/character.yaml`）:

```yaml
table: character
display_name: キャラクター
fields:
  - name: name
    type: string
    display_name: 名前
  - name: rarity
    type: enum
    display_name: レアリティ
    enum_ref: rarity
  - name: hp
    type: int
    display_name: HP
records:
  - id: 1
    name: 勇者アルス
    rarity: SSR
    hp: 1200
  - id: 2
    name: 魔法使いリナ
    rarity: SR
    hp: { value: 800, color: red, comment: 次回調整予定 }
view:
  column_widths: { name: 160, hp: 80 }
```

JSON で保存した場合（`tables/character.json`）:

```json
{
  "table": "character",
  "display_name": "キャラクター",
  "fields": [
    { "name": "name", "type": "string", "display_name": "名前" },
    { "name": "rarity", "type": "enum", "display_name": "レアリティ", "enum_ref": "rarity" },
    { "name": "hp", "type": "int", "display_name": "HP" }
  ],
  "records": [
    {
      "id": 1,
      "name": "勇者アルス",
      "rarity": "SSR",
      "hp": 1200
    },
    {
      "id": 2,
      "name": "魔法使いリナ",
      "rarity": "SR",
      "hp": { "value": 800, "color": "red", "comment": "次回調整予定" }
    }
  ],
  "view": {
    "column_widths": { "name": 160, "hp": 80 }
  }
}
```

画面で D2 を 800 から 1000 に変えて保存したときの差分（YAML の場合）:

```diff
   - id: 2
     name: 魔法使いリナ
     rarity: SR
-    hp: { value: 800, color: red, comment: 次回調整予定 }
+    hp: { value: 1000, color: red, comment: 次回調整予定 }
```

## 2. 決定済みの前提（2026-10-13 確認）

| ID | 論点 | 決定 | 帰結 |
|---|---|---|---|
| D-1 | シートの形 | **型付きテーブル**。列＝型を持つフィールド、行＝レコード | 列ごとに入力制限がかかる（例: `int` 列に `abc` は入らない）。ファイルは「列定義＋レコードの並び」。Googleスプレッドシートの「データの入力規則」を、列ごとに常に設定した状態に相当する |
| D-2 | リソースファイルの形式 | **YAML と JSON の両対応**。プロジェクトごとにどちらか一方を選ぶ | データモデルは共通にし、読み書きの層だけを差し替える |
| D-3 | 実行形態 | **ブラウザで動く Web アプリ**（インストール不要） | フォルダを直接読み書きできないブラウザでも、代わりの方式で使えるようにする（D-11、§10.1） |
| D-4 | データ規模 | 1 テーブル最大 **1 万行 × 50 列程度**、1 プロジェクト **100 テーブル程度** | 性能の要件（§10.2）の基準になる |
| D-5 | 出力ファイル | **出力する**。形式は JSON か YAML をプロジェクト設定で選ぶ（既定は JSON） | §9 |
| D-6 | 型の追加 | `list<enum>`、`list<float>`、日時（`datetime`）、64 ビット整数（`int64`）を加える | 型は全 11 種（DR-13） |
| D-7 | 保存 | **手動保存**（Ctrl+S）。自動保存はしない | Googleスプレッドシートとの違い（§4） |
| D-8 | 表示設定 | 列幅などの表示設定は**テーブルファイルに含める** | DR-06 |
| D-9 | YAML に直接書かれたコメント | 保存時に**警告なしで消してよい** | DR-44 |
| D-10 | スクリーンリーダー | **対応しない**（キーボードだけでの操作は必須） | GUI ライブラリは、Canvas で描くものも選べる |
| D-11 | Firefox / Safari | **非対応とはしない**。できる範囲で使えるようにする | §10.1 のダウンロード保存方式。うまく動かない場合は失敗してよい |

D-1 の補足: 自由セル型（どのセルにも何でも入り、`=B2*2` のように番地で参照する形）は採用しない。理由は、ゲームが読むデータには列ごとの型の保証が必要で、自由セル型では出力時に構造を推定する規則を別に作る必要があるためである。

## 3. 用語

| 用語 | 定義 | ファイル上のキー |
|---|---|---|
| プロジェクト | 1 つのマスターデータ一式。プロジェクト設定ファイル（§6.1）を置いたフォルダ | — |
| テーブル（シート） | 1 種類のマスターデータ（例: キャラクター）。画面上の 1 シート。1 テーブル＝1 ファイル | `table` |
| フィールド（列） | 名前と型を持つ列の定義 | `fields` |
| レコード（行） | テーブルの 1 行 | `records` |
| 共通列 | 全テーブルに自動で付く列（`id` など） | `base_fields` |
| 主キー | レコードを一意に識別する列。既定は `id` | `primary: true` |
| SimpleCell / RichCell | 値だけのセル／値にセル色・メモ・セル単位式を付けたセル | `hp: 1200` ／ `hp: { value: 800, color: red }` |
| 列レベル式 | 列全体の既定値を計算する式 | 列定義の `formula` |
| セル単位式 | 特定のセルだけに設定する式。`=` で始めて入力する | RichCell の `override` |
| メモ | セルに付ける注記。Googleスプレッドシートの「メモ」にあたる | RichCell の `comment` |
| セル色 | プロジェクトで定義したプリセットから選ぶ背景色 | RichCell の `color` |
| 表示設定 | 列幅・固定する列の数・非表示の列 | テーブルファイルの `view` |
| エラー／警告 | 検査ルールへの違反／異常値の検知 | `validation` ／ `anomaly` |
| リソースファイル | 編集対象の YAML / JSON ファイル | — |
| 出力ファイル | リソースファイルから作る、ゲームが読むファイル。列定義・セル色・メモを除き、式を計算済みの値にしたもの | — |
| 正規形 | 同じデータなら必ず同じバイト列になる書き出し方（§6.4） | — |
| 直接保存方式 | ブラウザが、利用者の選んだフォルダのファイルを直接読み書きする方式（§10.1） | — |
| ダウンロード保存方式 | フォルダを読み込み専用で開き、保存は変更したファイルのダウンロードで行う方式（§10.1） | — |

## 4. スコープ（Googleスプレッドシートの機能の対応範囲）

R-1 を具体化するため、Googleスプレッドシートの主な機能ごとに、再現するかどうかを決める。

| Googleスプレッドシートの機能 | 本ツール | 備考 |
|---|---|---|
| セルの入力・編集、数式バー | 再現する | §5.1、§5.3 |
| 範囲選択・キーボード移動 | 再現する | §5.2 |
| コピー・切り取り・貼り付け（他アプリとの往復を含む） | 再現する | §5.4 |
| フィルハンドル（連続データの自動入力） | 再現する | §5.5 |
| 行・列の挿入・削除・移動 | 再現する | §5.6、§5.7 |
| 列幅の変更・固定・非表示（シートと一緒に保存される） | 再現する | §5.7、DR-06 |
| 並べ替え・フィルタ | 再現する | §5.8 |
| 検索と置換 | 再現する | §5.9 |
| 元に戻す・やり直し | 再現する | §5.11 |
| 塗りつぶしの色 | 一部を再現（プリセット色のみ） | §5.10 |
| メモ | 再現する | §5.10 |
| データの入力規則（プルダウン・数値範囲など） | 形を変えて再現（列の型と検査ルール） | §8 |
| 数式・関数 | 再現する（関数・演算子・結果は同じ。セル番地の代わりに列名で参照） | §7 |
| 数式のエラー表示（`#DIV/0!` など） | 再現する | §7 |
| 複数のシート、シートタブ | 再現する（1 シート＝1 テーブル＝1 ファイル） | §5.12 |
| 範囲の保護 | 形を変えて再現（列の編集不可設定） | §5.3 |
| 自動保存 | 再現しない（手動保存。D-7） | §5.13 |
| 文字の装飾（フォント・太字・罫線・配置） | 再現しない | リソースファイルに保存する意味がないため |
| 条件付き書式・グラフ・ピボットテーブル | 再現しない | 要望があれば将来検討 |
| 版の履歴 | 再現しない | ファイルの履歴は利用者側の仕組み（Git など）で管理する |
| 複数人での編集 | 本書では扱わない | 後から検討する |
| Googleスプレッドシート本体との連携（読み込み・同期） | 対象外 | 本ツールは独立したツール |

## 5. Googleスプレッドシート再現要件（画面と操作）

キー操作は Windows の表記で書く。Mac では Ctrl を ⌘ に読み替える。Googleスプレッドシート側の正しいキー割り当ては公式ヘルプ（付録）で確認する。

### 5.1 画面構成

| ID | 要件 | 優先度 |
|---|---|---|
| FR-UI-01 | メニューバーとツールバー | 必須 |
| FR-UI-02 | 数式バー: 選択中のセルの中身を表示・編集する。セル単位式のセルでは `=hp*2` のような式を表示し、列レベル式に従うセルでは列の式を「列の式」と区別して表示する。グリッドには計算結果を表示する | 必須 |
| FR-UI-03 | セル位置の表示（Googleスプレッドシートの名前ボックスにあたる）: `テーブル / 列名 / id` を表示し、入力するとそのセルへ移動する | 推奨 |
| FR-UI-04 | グリッド: 行番号の列と列ヘッダー（表示名・列名・型・式の有無の印） | 必須 |
| FR-UI-05 | 画面下部のシートタブと、全シートの一覧ボタン（Googleスプレッドシートと同じ）。タブには未保存の印とエラー件数を表示する | 必須 |
| FR-UI-06 | 問題パネル: 全テーブルのエラー・警告を一覧し、クリックすると該当セルへ移動する | 必須 |
| FR-UI-07 | セル情報パネル: 選択中のセルのセル色・メモ・検査メッセージ | 推奨 |

### 5.2 選択と移動

| ID | 要件 | 優先度 |
|---|---|---|
| FR-SEL-01 | 矢印キーで 1 セル移動。Tab / Shift+Tab で左右、Enter / Shift+Enter で上下 | 必須 |
| FR-SEL-02 | Ctrl+矢印でデータの端へ移動。Ctrl+Home / Ctrl+End で先頭 / 末尾へ移動 | 必須 |
| FR-SEL-03 | ドラッグ、Shift+クリック、Shift+矢印、Ctrl+Shift+矢印で矩形の範囲を選択 | 必須 |
| FR-SEL-04 | 範囲をドラッグして表示領域の外に出たら、自動でスクロールする | 必須 |
| FR-SEL-05 | 行番号のクリックで行全体、列ヘッダーのクリックで列全体、Ctrl+A で全体を選択（並べ替えは列ヘッダーのメニューから行う） | 必須 |
| FR-SEL-06 | Ctrl+クリックで離れた複数の範囲を選択 | 将来 |

### 5.3 入力と編集

| ID | 要件 | 優先度 |
|---|---|---|
| FR-EDT-01 | 選択中のセルで文字を打つと上書き入力を始める。Enter / F2 / ダブルクリックでは既存の値を残して編集を始める。Esc で取り消す | 必須 |
| FR-EDT-02 | Delete / Backspace で選択範囲の値を消す（未入力に戻す。DR-15）。セル色・メモは残す | 必須 |
| FR-EDT-03 | 型ごとの入力部品: `int` / `int64` / `float` は数値、`string` は文字列（セル内の改行を含む）、`bool` はチェックボックス（Space で切り替え）、`enum` は絞り込み付きのプルダウン、`list<enum>` は候補からの複数選択、`datetime` は日付と時刻の選択部品、その他のリスト型は要素ごとの部品（タグ入力）、参照列は参照先の候補（主キーと名前を並べて表示） | 必須（リスト型・参照列は推奨） |
| FR-EDT-04 | `=` で始まる入力はセル単位式として保存する。先頭に `'` を付けると文字列として扱う（Googleスプレッドシートと同じ） | 必須 |
| FR-EDT-05 | 型に合わない入力は確定させず、入力内容を残したまま理由を表示する（例: `int` 列に `12a` →「整数を入力してください」）。黙って捨てたり、別の値に置き換えたりしない | 必須 |
| FR-EDT-06 | 編集できない列（`editable: false`、自動採番の列）は入力を受け付けず、見た目でも区別する | 必須 |
| FR-EDT-07 | 数式バーとセル内の編集で、列名と関数名を入力補完する | 推奨 |

### 5.4 コピー・切り取り・貼り付け

| ID | 要件 | 優先度 |
|---|---|---|
| FR-CLP-01 | Ctrl+C / Ctrl+X / Ctrl+V で範囲をコピー・切り取り・貼り付け | 必須 |
| FR-CLP-02 | Googleスプレッドシート・Excel との間で、範囲をそのまま往復できる（タブ区切りテキスト。改行やタブを含むセルも崩れない） | 必須 |
| FR-CLP-03 | 1 セルをコピーして範囲に貼ると、範囲全体を同じ値で埋める | 必須 |
| FR-CLP-04 | 貼り付ける値は、貼り付け先の列の型に変換する。1 セルでも変換できなければ貼り付け全体を取りやめ、失敗したセルの一覧を示す | 必須 |
| FR-CLP-05 | 貼り付けがレコードの末尾を超えたら行を追加する（主キーは採番する） | 推奨 |
| FR-CLP-06 | 切り取りと貼り付けで、値・セル色・メモ・セル単位式を移動する。範囲の枠をドラッグしても移動できる | 推奨 |
| FR-CLP-07 | Ctrl+Shift+V で値のみを貼り付ける（セル色・メモ・式は持ち込まない） | 推奨 |

|---|---|---|

| FR-FIL-05 | 連番入力: 開始値と増分を指定して範囲を埋める | 推奨 |

| ID | 要件 | 優先度 |

| FR-COL-03 | 列名の変更。同じテーブルの式、他テーブルの `ref` の定義、`REF()` の式の中の参照もまとめて書き換える | 推奨 |

### 5.8 並べ替えとフィルタ

## 6. リソースファイル要件（YAML / JSON）

### 6.1 プロジェクトの構成

| ID | 要件 | 優先度 |
|---|---|---|
| DR-01 | プロジェクトのルートにプロジェクト設定ファイルを 1 つ置き、ツールはこのファイルがあるかどうかでプロジェクトを認識する | 必須 |
| DR-02 | プロジェクト設定でリソースファイルの形式（`yaml` か `json`）を 1 つ指定する。1 つのプロジェクトの中で混在させない。指定と違う拡張子のテーブルファイルがあれば警告する | 必須 |
| DR-03 | プロジェクト設定に、ファイル形式の版数（`format_version`）を持たせる。将来ファイル形式を変えたとき、変換が必要かをツールが判断できるようにするため | 必須 |
| DR-04 | テーブルの識別子はテーブルファイルの中の `table` に一本化する。ファイル名は `<table>.<拡張子>` とし、一致しなければ警告する | 必須 |
| DR-05 | 共通設定（列挙型・共通列・セル色）とテーブルファイルの置き場所を、プロジェクト設定で指定できる | 推奨 |
| DR-06 | 表示設定（列幅・固定する列の数・非表示の列）は、テーブルファイルの `view` に保存する（D-8）。表示だけの並べ替えとフィルタの状態は保存しない | 必須 |
| DR-07 | プロジェクト設定に、日時の表示・入力に使うタイムゾーンを持たせる（省略時はブラウザのタイムゾーン） | 必須 |

プロジェクト設定ファイルの例（キー名は確定ではない）:

```yaml
# masterdata-maker.yaml
format_version: 1
storage:
  format: yaml          # リソースファイルの形式: yaml | json
timezone: Asia/Tokyo    # 日時の表示・入力に使うタイムゾーン
paths:
  tables: tables/
  config: config/
output:
  format: json          # 出力ファイルの形式: json | yaml | csv | protobuf（既定は json）
  out_dir: build/
```

### 6.2 テーブルファイル

| ID | 要件 | 優先度 |
|---|---|---|
| DR-10 | テーブルファイルは `table`（識別子）、`display_name`、`fields`（列定義の配列）、`records`（レコードの配列）、`view`（表示設定。省略可）、`proto`（Protocol Buffers のフィールド番号。省略可。P-63）を持つ | 必須 |
| DR-11 | セルは SimpleCell（値だけ）か RichCell（`{ value, override, color, comment }`）。セル色・メモ・セル単位式が無いセルは値だけで保存する。RichCell の `value` にはリストも入れられる | 必須 |
| DR-12 | 列定義に知らないキーがあれば、読み込み時にエラーにする（例: フィールドの直下に書いた `required` は、`validation.required` の書き間違いとして見つかる） | 必須 |
| DR-13 | フィールド型は 11 種: `int` `int64` `float` `string` `bool` `enum` `datetime` `list<int>` `list<float>` `list<string>` `list<enum>`。`enum` と `list<enum>` は `enum_ref` が必須 | 必須 |
| DR-14 | 列定義のキー: `name` `type` `display_name` `description` `export` `editable` `primary` `auto` `enum_ref` `ref` `formula` `default` `validation` `anomaly` | 必須 |
| DR-15 | 未入力と空文字 `""` は区別しない。未入力のセルはキーを書かない（`""` を読み込んだ場合も未入力として扱い、次の保存でキーを消す）。未入力のセルの出力値は、列の `default` があればその値、無ければ `null` | 必須 |
| DR-16 | 主キーは一意でなければならない。行を追加するときは、`auto: increment` の列に「既存の最大値＋1」を採番する | 必須 |
| DR-17 | `ref` は `<テーブル>.<列>` の形で、参照先の列は主キーか一意制約付きの列に限る | 必須 |
| DR-18 | `datetime` は、ファイル上は UTC からの時差付きの ISO 8601 形式の文字列で書く（例: `"2026-10-13T12:00:00+09:00"`）。秒まで持つ。画面ではプロジェクト設定のタイムゾーン（DR-07）で表示・入力する | 必須 |
| DR-19 | `int64` は ±9,223,372,036,854,775,807 までの整数。ファイル上は引用符なしの数値で書き、ツールは精度を落とさずに読み書きする（JavaScript の通常の数値ではなく BigInt で扱う） | 必須 |

### 6.4 書き出し規則（正規形）

目的: 画面で 1 セル変えたら、ファイルの差分もおおむね 1 行にする（R-2）。

| ID | 要件 | 優先度 |
|---|---|---|
| DR-30 | 同じデータは必ず同じバイト列で書き出す。読み込んで何も変えずに保存したら、正規形のファイルは 1 バイトも変わらない | 必須 |
| DR-31 | 文字コードは UTF-8（BOM なし）、改行は LF、ファイル末尾に改行を 1 つ、インデントは半角スペース 2 つ | 必須 |
| DR-32 | キーの順序を固定する。テーブルは `table` → `display_name` → `fields` → `records` → `view` → `proto`。レコードの中は列定義の順（共通列が先）。列定義の中は DR-14 の順 | 必須 |
| DR-33 | YAML では、レコードは 1 フィールドを 1 行で書く。値だけのリストは 1 行（`[1, 3, 7]`）、RichCell も 1 行（`{ value: 800, color: red }`）で書く | 推奨 |
| DR-34 | 列定義に無いキーがレコードにあれば、消さずにレコードの末尾に残し、警告する | 推奨 |
| DR-35 | 小数は、読み戻して同じ値になる最も短い 10 進表記で書く（JavaScript の `Number.prototype.toString` と同じ）。`NaN` と `Infinity` は保存できない | 必須 |
| DR-36 | `int` は安全な整数の範囲（±9,007,199,254,740,991。`Number.MAX_SAFE_INTEGER`）に限る。超える値が要る列は `int64` にする | 必須 |

### 6.5 YAML の規則

背景: YAML 1.1 では `yes` / `no` / `on` / `off` / `y` / `n` なども真偽値として読まれる（例: 国コード `NO` が `false` になる）。YAML 1.2 では真偽値は `true` / `false` だけになったが、1.1 に従うパーサーはまだ広く使われている。また `1.10` はどちらの版でも数値の 1.1 として読まれ、YAML 1.1 では `2026-10-13` のような値が日時として読まれる。ゲーム側や他のツールがどちらの版のパーサーで読むかは、本ツールからは制御できない（付録）。

| ID | 要件 | 優先度 |
|---|---|---|
| DR-40 | YAML 1.2 で書き出す | 必須 |
| DR-41 | 文字列型の値が、YAML 1.1 と 1.2 のどちらかで文字列以外（数値・真偽値・null・日時）として読まれうるなら、必ず引用符で囲む。`datetime` の値は常に引用符で囲む | 必須 |
| DR-42 | 読み込むときは、YAML のタグではなく列定義の型で値を解釈して検査する。例: `string` 列に引用符なしの `1.10` があれば、数値として読まれた旨を警告する（元の表記 `1.10` を文字列として復元できれば、なお良い） | 必須（復元は推奨） |
| DR-43 | アンカーとエイリアス（`&` と `*`）、独自のタグは、読み込み時にエラーにする。書き出すときに再現できず、保存すると構造が変わってしまうため | 必須 |
| DR-44 | YAML ファイルに直接書かれたコメント（`#`）は、保存時に残さない。警告もしない（D-9） | 必須 |

DR-41 の例:

```yaml
code: "NO"                             # 引用符なしだと YAML 1.1 で false になる
label: "1.10"                          # 引用符なしだと数値の 1.1 になる
note: "null"                           # 引用符なしだと null になる
start_at: "2026-10-13T12:00:00+09:00"  # datetime は常に引用符で囲む
name: 勇者アルス                        # 誤読の余地が無いので引用符なし
```

## 7. 数式要件

式の書き方は Googleスプレッドシートと同じにする（R-1）。違いは、セル番地の代わりに同じレコードの列名を書くことだけである。D-1（型付きテーブル）のため、他の行の参照や列全体の集計はしない。他のテーブルの値は `REF()` で参照する。

例:

| Googleスプレッドシート | 本ツール |
|---|---|
| `=IF(C2="SSR", D2*2, D2)` | `=IF(rarity = "SSR", hp * 2, hp)` |
| `=ROUND(D2 * (1 + E2 / 100))` | `=ROUND(hp * (1 + defense / 100))` |

| ID | 要件 | 優先度 |
|---|---|---|
| FR-FML-01 | 列レベル式とセル単位式の 2 段。値の優先順位は「セルの値 ＞ セル単位式 ＞ 列レベル式」 | 必須 |
| FR-FML-02 | 演算子は Googleスプレッドシートと同じ: `+` `-` `*` `/` `^`（累乗）、`&`（文字列の連結）、`=` `<>` `<` `>` `<=` `>=`、`%`（百分率。`50%` は 0.5）。論理演算は `AND` / `OR` / `NOT` 関数で書く。文字列は `"…"`（`"` 自体は `""` と書く）、真偽値は `TRUE` / `FALSE` | 必須 |
| FR-FML-03 | 関数は下の表のものを用意し、名前・引数・結果を Googleスプレッドシートと同じにする。関数名は大文字と小文字を区別しない | 必須 |
| FR-FML-04 | 独自の関数は `REF(テーブル名, キーまたはキーのリスト, 列名)` だけとする。参照先テーブルの主キーで照合し、キーがリストならリストを返す。例: `SUM(REF("skill", skill_ids, "cost"))` | 必須 |
| FR-FML-05 | リスト型の値は、Googleスプレッドシートの範囲（複数のセル）と同じに扱う。例: `SUM(costs)`、`COUNTIF(elements, "火") > 0` | 必須 |
| FR-FML-06 | `datetime` の値は比較（`<` など）と日付の関数で扱える。実行するたびに結果が変わる関数（`NOW` `TODAY` `RAND` `RANDBETWEEN`）は使えない | 必須 |
| FR-FML-07 | `int64` の列の計算は整数のまま精度を落とさずに行う。小数と混ぜたらエラーにする | 必須 |
| FR-FML-08 | 式は一度構文解析して構文木にし、計算と依存関係の抽出の両方に使う | 必須 |
| FR-FML-09 | 依存関係の順に計算する（列定義の順ではない）。例: `a = b + 1`、`b = 10` なら、`a` が `b` より前の列でも `a` は `11` | 必須 |
| FR-FML-10 | `IF` は選ばれなかった側を計算しない。例: `IF(1 = 1, 1, 1 / 0)` は `1` を返し、エラーにならない。`AND` / `OR` などの評価の仕方も Googleスプレッドシートに合わせる | 必須 |
| FR-FML-11 | 循環参照は、列レベル式・セル単位式・`REF()` を通したテーブル間の参照のすべてで検出する。文字列の中に列名と同じ語があっても依存とみなさない | 必須 |
| FR-FML-12 | 計算結果を列の型で検査する。例: `int` 列の式が `1.5` を返したらエラーにする（勝手に丸めない） | 必須 |
| FR-FML-13 | エラーのセルには、Googleスプレッドシートと同じエラー値（`#DIV/0!` `#VALUE!` `#NAME?` `#REF!` など）を表示する。エラーは種類・列・レコードの主キー・式の中の位置（何文字目か）を持ち、検査結果に含める | 必須 |
| FR-FML-14 | セルを編集したら、そのセルに依存する式だけを計算し直す | 推奨 |
| FR-FML-15 | 式の計算に JavaScript の `eval` や `Function` を使わない | 必須 |
| FR-FML-16 | 出力には、式ではなく計算結果を書く | 必須 |

FR-FML-03 の関数:

| 分類 | 関数 |
|---|---|
| 論理 | `IF` `AND` `OR` `NOT` |
| 集計 | `SUM` `AVERAGE` `MIN` `MAX` `COUNT` `COUNTA` `COUNTIF` |
| 数学 | `ABS` `ROUND` `ROUNDUP` `ROUNDDOWN` `FLOOR` `CEILING` `INT` `MOD` `POWER` `SQRT` |
| 文字列 | `CONCATENATE` `LEN` `LEFT` `RIGHT` `MID` `UPPER` `LOWER` `TRIM` `SUBSTITUTE` |
| 型変換 | `VALUE` `TO_TEXT` |
| 日時 | `DATE` `YEAR` `MONTH` `DAY` `HOUR` `MINUTE` `SECOND` |
| 独自 | `REF`（FR-FML-04） |

## 8. 入力規則・検査要件

Googleスプレッドシートの「データの入力規則」にあたる部分。D-1 により、列の型は常に適用される入力規則になり、そのうえで列ごとに追加のルールを付けられる。

| ID | 要件 | 優先度 |
|---|---|---|
| FR-VAL-01 | エラー（`validation`）と警告（`anomaly`）の 2 段階にする | 必須 |
| FR-VAL-02 | 検査するのは、式を計算した後の値 | 必須 |
| FR-VAL-03 | 設定しなくても常に行う検査: 型、列挙型の値（`list<enum>` は要素ごと）、参照先の存在、主キーの一意性、整数の範囲（DR-19、DR-36）、`datetime` の形式（DR-18）、リストの要素の型 | 必須 |
| FR-VAL-04 | 列ごとに付けられるルール: `required`、`min`、`max`、`max_length`（文字数）、`max_items`（リストの要素数）、`regex`、`unique`。`min` / `max` は `datetime` にも使える | 必須 |
| FR-VAL-05 | 警告のルール: `warn_above`（上限）、`warn_below`（下限）、`warn_deviation`（平均から標準偏差の何倍離れたら） | 必須 |
| FR-VAL-06 | `warn_delta`（前回からの変化量）は、何と比べるかを決める必要があるため、初版では外す | 将来 |
| FR-VAL-07 | 列定義そのものの検査: 知らないキー（DR-12）、列名の重複、列名の書式（英小文字・数字・`_`。先頭は数字以外。`true` / `false` は不可）、存在しない列挙型や参照先、式の構文エラー | 必須 |
| FR-VAL-08 | 結果は、テーブル・レコードの主キー・列・重大度・メッセージを持つ。並べ替えても指す先が変わらないように、配列の番号ではなく主キーで示す | 必須 |
| FR-VAL-09 | 画面では、編集してから 300 ミリ秒以内に全テーブルを検査し直し、セルの枠・問題パネル・シートタブの件数に反映する | 必須 |
| FR-VAL-10 | 利用者が書いた正規表現で画面が固まらないよう、検査は画面とは別のスレッド（Web Worker）で動かし、時間制限を設ける。例: `(a+)+$` に `aaaa…a!` を与えると、照合時間が指数関数的に増える（正規表現によるサービス拒否、ReDoS） | 推奨 |
| FR-VAL-11 | 画面と CLI で同じ検査処理を使う | 必須 |

## 9. 出力・CLI 要件

### 9.1 出力（ゲームが読むファイル）

リソースファイルには、ゲームが使わない情報（列定義・セル色・メモ）と、ゲーム側では計算できない式が入る。そのため、値だけにした出力ファイルを別に作る（D-5）。

リソースファイル（YAML プロジェクトの場合）:

```yaml
fields:
  - { name: hp, type: int }
  - { name: defense, type: int }
  - { name: effective_hp, type: float, formula: hp * (1 + defense / 100) }
records:
  - id: 2
    hp: { value: 800, color: red, comment: 次回調整予定 }
    defense: 30
```

出力ファイル（JSON の場合）:

```json
[
  {
    "id": 2,
    "hp": 800,
    "defense": 30,
    "effective_hp": 1040
  }
]
```

出力ファイル（CSV の場合。1 行目は列名、未入力は空欄、リストは JSON の配列。P-62）:

```csv
id,hp,defense,effective_hp
2,800,30,1040
```

出力ファイル（Protocol Buffers の場合。テーブルごとにスキーマ `character.proto` とデータ `character.pb` を出す。`.pb` は `CharacterTable` を符号化したもの。P-63）:

```proto
syntax = "proto3";

package masterdata_maker;

message Character {
  optional int64 id = 1;
  optional int64 hp = 2;
  optional int64 defense = 3;
  optional double effective_hp = 4;
}

message CharacterTable {
  repeated Character records = 1;
}
```

| ID | 要件 | 優先度 |
|---|---|---|
| FR-OUT-01 | 出力ファイルの形式は、JSON・YAML・CSV・Protocol Buffers から選ぶ。既定はプロジェクト設定の `output.format`（無ければ JSON）で、画面の出力のダイアログと CLI の `export --format` でその回だけ変えられる。リソースファイルの形式とは別に選べる。CSV と Protocol Buffers の書き方は P-62・P-63（実装計画書） | 必須 |
| FR-OUT-02 | 出力の決まり: `export: false` の列は除く、式は計算結果にする、セル色とメモは含めない、共通列は含める、1 テーブル＝1 ファイル＝レコードの配列 | 必須 |
| FR-OUT-03 | 出力ファイルにも正規形（DR-30〜36、YAML は DR-40〜41、JSON は DR-50〜51）を当てはめる。キーは列定義の順。同じ入力からは必ず同じ出力にする | 必須 |
| FR-OUT-04 | 未入力のセルは、列の `default` があればその値、無ければ `null` を出力する（DR-15） | 必須 |
| FR-OUT-05 | 検査エラーがあるときは出力しない（CLI は終了コード 1）。`--force` を付けたときだけ出力する | 必須 |
| FR-OUT-06 | 画面から、全テーブル（または選んだテーブル）を出力する。直接保存方式ではプロジェクト設定の出力先フォルダへ書き込み、ダウンロード保存方式ではダウンロードする | 推奨 |
| FR-OUT-07 | 出力する版（セマンティック バージョニング）を指定できる。指定すると、`version` 列がその版以下のレコードだけを出力する（`version` が空のレコードは常に出す）。指定が無ければすべてのレコードを出す。画面の出力のダイアログと CLI の `export --until` で指定する。主キーは版を指定しても一意のままとし、版ごとの値の違いはリソースファイルをブランチで分けて管理する。比べ方と検査は P-64（実装計画書） | 必須 |

### 9.2 CLI

| FR-CLI-02 | `export`: 出力する（§9.1） | 必須 |

## 10. 非機能要件

### 10.1 動作環境

| ID | 要件 | 優先度 |
|---|---|---|
| NFR-01 | 対象ブラウザは、デスクトップ版の Chrome・Edge・Firefox・Safari（最新の安定版）。非対応のブラウザは設けない（D-11） | 必須 |
| NFR-02 | 直接保存方式: フォルダを直接読み書きする API（File System Access API の `showDirectoryPicker()`）が使えるブラウザでは、利用者の選んだフォルダのファイルを直接読み書きする。2026-10-13 時点で MDN は Chrome / Edge 86 以降を対応、Firefox / Safari を非対応としている（付録） | 必須 |
| NFR-03 | ダウンロード保存方式: NFR-02 の API が使えないブラウザでは、フォルダ選択用の `<input type="file" webkitdirectory>` でフォルダを読み込む（MDN では 2025-08 から主要ブラウザで使える）。保存では変更したファイルをダウンロードする（1 ファイルならそのファイル、複数ならフォルダ構成を保った ZIP）。この方式で読み込みや保存に失敗する場合は、失敗してよい（例: Safari でフォルダではなくファイルが選べてしまう不具合の報告がある） | 推奨 |
| NFR-04 | ローカルのフォルダを開くときに NFR-02・NFR-03 のどちらの方式にするかは、ブラウザの名前ではなく API が使えるかどうかで自動的に決める（GitHub 方式 FR-GH-01 は利用者が開始画面で選ぶ）。ブラウザ側の対応が変わっても、そのまま追従できるようにするため | 必須 |
| NFR-05 | ダウンロード保存方式では、使えない機能（前回のフォルダの記憶 FR-FIO-01、外部での変更の検知 FR-FIO-07、フォルダへの直接保存）を画面に示す | 必須 |
| NFR-06 | HTTPS の静的ホスティングで配る（`showDirectoryPicker()` は HTTPS などの安全な環境でしか使えない） | 必須 |
| NFR-07 | サーバーを持たない。データを外部に送らない。ただし GitHub 方式（FR-GH-01）を選んだときだけ、トークンと、フォルダの読み込み・コミット・プルリクエストに要るデータを、利用者が指定した GitHub のリポジトリ（api.github.com）へ送る | 必須 |

## 11. 判断の記録

§2 の決定以外で、作成者が R-1・R-2・§2 から導いて決めた事項。

| # | 事項 | 判断 | 理由 |
|---|---|---|---|
| J-01 | 式の書き方 | Googleスプレッドシートと同じ関数名・引数・演算子・結果にする（§7） | R-1。名前だけでなく引数の決まりも合わせる必要がある。例: Googleスプレッドシートの `MID("abc", 1, 1)` は `"a"`（1 から数える）。0 から数える独自の関数を作ると、同じ見た目の式で結果が変わる |
| J-02 | 未入力と空文字 | 区別しない。未入力の出力値は列の `default`、無ければ `null`（DR-15） | 画面上で空欄と空文字は見分けがつかず、利用者が使い分けられない。ゲーム側で `""` が欲しい列は `default: ""` で表せる |
| J-03 | 検査エラーがあるときの保存 | 保存は止めない。出力で止める（FR-FIO-08、FR-OUT-05） | 保存を止めると、ブラウザを閉じたときに作業が失われる。ゲームに届くのは出力ファイルなので、そこで止めれば不正なデータは出ていかない |
| J-04 | テーブル一覧の形 | 画面下部のシートタブと全シートの一覧ボタン（FR-UI-05） | R-1（Googleスプレッドシートと同じ） |
| J-05 | GUI ライブラリ | 要件定義書では選定条件（§10.4）までを決め、ライブラリは設計工程で選ぶ | 要件定義で決める事項ではない |
| J-06 | `version` 列 | 文字列で手入力し、セマンティック バージョニングとして並べ替える（DR-21） | 自動で上げる規則（どの変更で上げるか）が無い |
| J-07 | 大きなテーブルのファイル分割 | 分割しない | R-2（1 シート＝1 ファイル）。D-4 の規模なら 1 ファイルで扱える |
| J-08 | 保存する表示設定の範囲 | 列幅・固定する列の数・非表示の列だけを保存し、表示だけの並べ替えとフィルタは保存しない（DR-06） | 並べ替えやフィルタのたびにファイルに差分が出るのを避ける |
| J-09 | `datetime` の書き方 | UTC からの時差付きの ISO 8601 形式の文字列（DR-18） | 時差が無いと、タイムゾーンの違う環境で読んだときに時刻がずれる。ISO 8601 は主要なプログラミング言語に読み込み処理がある |
| J-10 | `int64` の書き方 | 引用符なしの数値（DR-19） | ゲーム側で使われる言語の多く（C#、C++ など）は 64 ビット整数を数値のまま読める。文字列にすると、ゲーム側で変換が要る |
| J-11 | 実行のたびに結果が変わる関数 | 使えない（FR-FML-06） | 出力のたびに値が変わり、同じ入力から同じ出力を作れなくなる（FR-OUT-03） |
| J-12 | Firefox / Safari での保存方式 | フォルダを読み込み専用で開き、保存はダウンロードで行う（NFR-03） | 利用者が選んだフォルダへブラウザから直接書き込む標準の手段は、File System Access API の他に見当たらなかった（2026-10-13 時点の調査範囲） |
| J-13 | 列名の書式 | 英小文字・数字・`_` に限る（FR-VAL-07） | ゲーム側のコードで、列名をそのまま変数名やキー名に使えるようにするため。日本語の名前は `display_name` に書く |
| J-14 | GitHub 方式の認証 | 利用者が作った fine-grained personal access token を画面で入れる（FR-GH-01、FR-GH-05。2026-10-22 に利用者が決定） | サーバーを持たない（NFR-07）まま使える方式がこれしか無い。OAuth・GitHub App のログインは、コードをトークンに交換する GitHub の端点がブラウザからの呼び出し（CORS）に対応しておらず、client secret を持つ中継サーバーが要る（P-67。2026-10-22 時点の公開情報で、手元では未検証）。fine-grained のトークンは対象のリポジトリと権限（Contents・Pull requests）を絞れる |
