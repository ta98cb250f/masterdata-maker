## 1. 確定した方針（2026-10-13 確認）

| ID | 論点 | 決定 |
|---|---|---|
| C-1 | グリッドの実装方式 | 描画は React 19 の DOM で自前で作り、仮想スクロールだけ `@tanstack/virtual-core` を使う |
| C-2 | 検査ルール `regex` の正規表現エンジン | `re2js`（RE2 構文）。検査は Web Worker で動かし、時間制限も設ける（FR-VAL-10） |
| C-3 | Git の運用 | `main` には計画書だけを置き、実装は作業ブランチ `claude/sheetcraft-v1` に段階ごとにコミットして push する。PR は依頼があるまで作らない |
| C-4 | YAML の読み込みの速さ（2026-10-14 確認） | 本ツールが書き出す正規形の YAML だけを速く読む専用の処理を追加する。正規形と判定できない入力は `yaml` ライブラリで読み直し、両者の結果が一致することを自動テストで確かめる。理由: `yaml` ライブラリだけでは 1 万行 × 50 列（約 10MB）の読み込みに約 10.5 秒かかり、NFR-11 を満たせない見込みのため |
| C-5 | 実装の進め方（2026-10-13 指示） | 実装はサブエージェントに任せ、親は設計の指示・成果物の確認・テストの実行・コミットを受け持つ |

## 3. 全体構成

### 3.1 リポジトリの構成

pnpm のワークスペースで、3 つのパッケージに分ける。

```
packages/
  core/                 GUI に依存しない処理（NFR-24）。画面と CLI で共有する
    src/model/          データモデル（プロジェクト・テーブル・列定義・レコード・セル）
    src/io/             読み書き（YAML / JSON のパーサーと正規形の書き出し、プロジェクトの読み込み）
    src/formula/        数式（字句解析・構文解析・評価・関数・依存関係）
    src/validate/       検査（型・入力規則・警告・列定義の検査）
    src/export/         出力ファイルの生成
    src/edit/           編集操作（パッチ・コマンド・元に戻す履歴・入力値の変換）
    src/sheet/          表計算の操作ロジック（NFR-23: 選択範囲、クリップボード変換、フィルの推定、並べ替え・フィルタ、検索と置換）
    src/i18n/           文言ファイル（ja.json / en.json）と置換関数
  cli/                  Node.js の CLI（validate / export / new / fmt / convert）
  app/                  ブラウザの Web アプリ（React）
    src/fs/             ファイルの読み書き方式（直接保存方式・ダウンロード保存方式）
    src/grid/           自前のグリッド（描画・マウス・キーボード）
    src/components/     メニューバー・ツールバー・数式バー・シートタブ・各パネル・ダイアログ
    src/worker/         検査用の Web Worker
    e2e/                Playwright の画面テスト（§5.17 の受け入れ基準）
samples/
  basic-yaml/           サンプルのプロジェクト（YAML）
  basic-json/           同じ内容の JSON 版
docs/
  requirements.md       要件定義書
  plan.md               本書
```

### 3.2 依存の向き

```
app ──→ core ←── cli
 │
 └─→ worker（core を読み込む）
```

`core` は DOM と Node.js の API のどちらにも依存しない。ファイルの読み書きは、`core` が定める抽象的な入出力の型（`ProjectFs`）を通す。ブラウザの 2 方式と Node.js の実装は、それぞれ `app` と `cli` の側に置く。

## 4. データモデルと処理の流れ

### 4.1 データモデル

- **テーブル**: 識別子とは別に、内部用の不変の番号を持つ（名前の変更や元に戻す操作で、指す先が変わらないようにするため）
- **レコード**: 内部用の不変の番号と、フィールド名→セルの対応表を持つ。並べ替えや主キーの変更でも、内部番号は変わらない
- **セル**: 値だけなら値そのもの（数値・BigInt・文字列・真偽値・配列）を持ち、セル色・メモ・セル単位式があるときだけ RichCell のオブジェクトにする。1 万行 × 50 列の 50 万セルで、オブジェクトの数を抑えるため
- **型に合わない値**: ファイルに型と違う値があっても捨てずに保持し、検査でエラーにする（例: `int` 列の `"abc"`）。保存すると元の値のまま書き戻す

### 4.2 編集の流れ（元に戻す・Web Worker の同期）

1. 画面の操作は、`core/edit` のコマンド（例: 貼り付け）になる
2. コマンドは、最小単位の変更（パッチ）の列とその逆のパッチの列を作る。1 回の操作は 1 つのトランザクションとして履歴に積む（FR-HIS-03）
3. パッチをメインスレッドのモデルに当て、同じパッチを Web Worker に送る。Worker は同じ処理でモデルの複製を更新する
4. 数式は、メインスレッドで表示に必要なセルだけを遅延評価する。結果はキャッシュし、依存する列だけを無効にする（FR-FML-14）
5. Worker は変更のあったテーブルとそれを参照するテーブルだけを検査し直し、結果を返す（FR-VAL-09、NFR-12）。一定時間内に返らなければ Worker を止めて作り直し、時間切れを表示する（FR-VAL-10）

### 4.3 数式の評価

- 式は一度構文木にし、計算と依存関係の抽出の両方に使う（FR-FML-08）
- 評価はセル単位で、必要になったときに再帰的に計算する。評価中のセルの集合を持ち、同じセルに戻ってきたら循環参照とする（FR-FML-11）。`REF()` を通したテーブル間の参照も同じ仕組みで検出できる
- この方式では計算の順序が依存関係で自然に決まり、列定義の順序に左右されない（FR-FML-09）
- 依存関係のグラフは列の単位で静的に作り、編集したときに無効にする範囲を決めるのに使う

### 4.4 ファイルの読み書き

| 方式 | 読み込み | 保存 | 判定方法 |
|---|---|---|---|
| 直接保存方式 | `showDirectoryPicker()` | `createWritable()` → `close()` の完了を待つ（NFR-15） | `'showDirectoryPicker' in window` |
| ダウンロード保存方式 | `<input type="file" webkitdirectory>` | 1 ファイルならそのファイル、複数なら ZIP をダウンロード | 上記の API が無いとき（NFR-04） |
| CLI | Node.js の `fs/promises` | 一時ファイルに書いてから名前を変える | — |

## 5. 要件書に無い事項の判断

要件定義書に書かれていない点・曖昧な点について、R-1（Googleスプレッドシートの挙動を正解とする）・R-2・§2 から判断した。変更が必要なら指摘を受けて直す。

### 5.1 ファイル構成

| # | 事項 | 判断 | 理由 |
|---|---|---|---|
| P-01 | プロジェクト設定ファイルの名前 | `sheetcraft.yaml` か `sheetcraft.json`（§6.1 の例に従う）。両方あればエラー。設定ファイル自身の形式は拡張子で決め、`storage.format` とは独立させる | 設定ファイルを読む前に形式を知る必要があるため |
| P-02 | 共通設定のファイル | 共通設定のフォルダ（`paths.config`）に `enums`・`base_fields`・`colors` の 3 ファイルを置く。拡張子は `storage.format` に従う。ファイルが無ければ既定値（共通列は `id` と `version`、セル色は 8 色のプリセット、列挙型は無し）を使う | 種類ごとにファイルを分けると、差分がその種類の中に収まる |
| P-03 | 共通列の書き方 | テーブルファイルの `fields` には書かず、レコードの先頭に値を書く（§1 の例に従う） | 共通列の定義を 1 か所にまとめるため |
| P-04 | セル単位式の保存形式 | RichCell の `override` に、先頭の `=` を除いた式を書く（例: `{ override: hp * 2 }`）。列の `formula` と同じ書き方にする | 列レベル式とセル単位式で書き方を揃える |
| P-05 | `view` の既定値 | 列幅の既定は 100 ピクセル。全て既定値なら `view` キー自体を書かない | 既定のままのテーブルに余計な行を出さない |
| P-06 | シートタブの並び順 | テーブル識別子の昇順 | 並び順を保存する場所が要件に無い。保存すると差分が増える |

### 5.2 値と型

| # | 事項 | 判断 | 理由 |
|---|---|---|---|
| P-10 | 値の優先順位と `default` | 「セルの値 ＞ セル単位式 ＞ 列レベル式 ＞ 列の `default` ＞ 未入力」の順に決まる値を「実効値」とする。式の参照・検査・出力はすべて実効値に対して行う | 出力される値と、検査や他の式が見る値を一致させるため。`required` の列に `default` を付けると、未入力でもエラーにならない |
| P-11 | 空のリスト `[]` | 未入力と同じに扱う（DR-15 と同じ考え方）。読み込み時は未入力とし、次の保存でキーを消す | J-02 と同じく、画面上で見分けがつかない。ゲーム側で `[]` が要る列は `default: []` で表せる |
| P-12 | `null` | YAML の `null`・`~`・空の値と JSON の `null` は未入力として扱い、読み込み時に警告を出す。文字列・列挙型の列で元の表記がある場合（例: 引用符なしの `null`）は、DR-42 に従って元の表記を文字列として復元する | DR-15、DR-42 |
| P-13 | 式の結果の型 | 列の型と違えばエラーにし、暗黙の変換をしない（例: `string` 列の式が数値を返したらエラー。`TO_TEXT` で包む）。例外として、整数の数値は `int64` 列で BigInt として受け入れる | FR-FML-12。式の中の数値リテラルは通常の数値なので、`int64` 列の `=1000` を受け入れるため |
| P-14 | `int64` の割り算 | 割り切れれば BigInt、割り切れなければ `#NUM!` | FR-FML-07（精度を落とさない）と FR-FML-12（勝手に丸めない） |
| P-15 | 日時の計算 | 日時は日時の値として持ち、数値との足し算・引き算は日単位にする。日時同士の差は日数になる。`&` で連結したり数値の関数に渡したりすると、シリアル値（1899-12-30 からの日数）として扱う。`TO_TEXT` は表示形式 `YYYY-MM-DD HH:mm:ss` の文字列を返す | Googleスプレッドシートでは日時は日数のシリアル値なので、計算結果を揃えるため |
| P-16 | 画面と貼り付けでのリストの表記 | 要素を `, ` でつなぐ（例: `1, 3, 7`）。要素に `,` や `"`、前後の空白があるときは `"` で囲み、`"` は `""` と書く | Googleスプレッドシートとの貼り付けの往復（FR-CLP-02）で、リストが 1 セルに収まるため |
| P-17 | `bool` の入力 | `TRUE` / `FALSE`（大文字と小文字は問わない）と `1` / `0` を受け付ける | 他のツールから貼り付けたときの変換のため |
| P-18 | `enum` の入力 | 定義された値と完全に一致するか、大文字と小文字を無視して 1 つだけ一致すれば、定義された値にして受け付ける | 入力の手間を減らし、保存される値は定義どおりに保つ |
| P-19 | `datetime` の入力 | `YYYY-MM-DD`、`YYYY-MM-DD HH:mm`、`YYYY-MM-DD HH:mm:ss`（区切りは `/` も可）、時差付きの ISO 8601 を受け付ける。時差が無ければプロジェクトのタイムゾーンで解釈し、そのタイムゾーンの時差を付けて保存する。既存の値は、変更しない限り元の時差のまま保つ | DR-18、DR-30 |
| P-20 | 文字列の比較（並べ替え） | Unicode のコードポイント順（UTF-8 のバイト順と同じ）。空欄は昇順でも降順でも末尾 | FR-SRT-01 の「文字コード順」を、環境によらず同じ結果になる形にした。空欄の扱いは Googleスプレッドシートと同じ |
| P-21 | `ref` 列の型 | 参照先の列と同じ型、またはその型のリスト（例: `list<int>` で `skill.id` を参照） | FR-ANN-05 の `skill_ids: [1, 3]` の例 |

### 5.3 数式

| # | 事項 | 判断 | 理由 |
|---|---|---|---|
| P-30 | 式の中の列名 | 大文字と小文字を区別しない（`HP` も `hp` を指す） | Googleスプレッドシートのセル番地（`a1` と `A1` は同じ）に合わせる。列名は英小文字だけなので、曖昧さは生じない |
| P-31 | `REF()` の引数 | テーブル名と列名は文字列リテラルに限る。テーブルや列が無ければ `#REF!`、キーが見つからなければ `#N/A`（`VLOOKUP` と同じ） | 依存関係を静的に抜き出すため（FR-FML-11、FR-COL-03） |
| P-32 | リストを単独の値として使う | `costs + 1` のようにリストを単独の値として使うと `#VALUE!` | 範囲を単独の値として使えないのと同じ |
| P-33 | 循環参照の表示 | `#REF!`（メッセージは「循環参照」） | Googleスプレッドシートと同じ |
| P-34 | 数値を文字列にするときの桁数 | 有効数字 15 桁（例: `0.1 + 0.2 & ""` は `"0.3"`） | Googleスプレッドシートの表示に合わせる |
| P-35 | 構文エラーの表示 | `#ERROR!`（メッセージに何文字目かを含める） | Googleスプレッドシートと同じ |

### 5.4 画面と操作

| # | 事項 | 判断 | 理由 |
|---|---|---|---|
| P-40 | 読み込みエラーのあるテーブル | YAML / JSON の構文エラー、列定義の知らないキー（DR-12）、アンカー・エイリアス・タグ（DR-43）のあるテーブルは、エラーの内容だけを表示し、編集も保存もしない | 開いて保存すると、知らないキーや構造が消えてデータが変わる（NFR-17） |
| P-41 | フィルの数値の推定 | 等差なら等差で続ける。2 つ以上の数値が等差でなければ、最小二乗法の直線で延長する。数値以外は選択した値の並びを繰り返す。末尾が数字の文字列は数字を進め、桁数（ゼロ埋め）を保つ | Googleスプレッドシートと Excel は線形の傾向で延長する（§8 で未検証として扱う） |
| P-42 | 行と列の移動の操作 | 選択済みの行番号・列ヘッダーをドラッグして移動する | Googleスプレッドシートと同じ |
| P-43 | テーブルの削除と名前変更 | ファイルの削除と名前の変更は保存のときに行う。ダウンロード保存方式ではファイルを消せないので、手で消すファイル名を表示する | 手動保存（D-7）に合わせる |
| P-44 | 履歴の件数 | 200 件 | FR-HIS-04（100 件以上） |
| P-45 | サンプルの試用 | フォルダを選ばずに、組み込みのサンプルをブラウザのメモリ上で開ける（保存はダウンロード保存方式） | 初めて使うときに試せるようにするため。画面テストでも使う |

### 5.5 実装の途中で決めた事項（2026-10-15 追記）

|---|---|---|---|
| P-50 | `'` を付けた入力（FR-EDT-04） | `string` 系の列では `'` の後ろをそのまま文字列にする。それ以外の列では `'` の後ろを列の型で変換する（例: `int` 列の `'123` は数値 123） | 型付きテーブル（D-1）では、`int` 列に文字列を入れられないため |
| P-51 | `--force` で出力するときの、型に合わない値（FR-OUT-05） | `null` で出力する（2026-10-15 に利用者が決定）。式のエラーも `null`。検査ルール（`min` など）の違反や警告の値は、型には合っているのでそのまま出す | 出力ファイルの各列を「その型の値か `null`」に限り、ゲーム側が型を前提に読めるようにするため（D-1 の補足）。元の値はリソースファイルに残る |
| P-52 | テーブルを選んで出力するときの検査の範囲（FR-OUT-05） | 選んだテーブルと共通設定だけを検査し、選ばなかったテーブルのエラーでは止めない | 「テーブル単位で止める」と読んだ。参照先のエラーが式の結果に響く場合は、選んだテーブルの式のエラーとして見つかる |

| P-55 | 貼り付けの敷き詰め（FR-CLP-03 の拡張） | 貼り付け先がコピー元のちょうど整数倍なら敷き詰める | Excel の規則。Googleスプレッドシートとの突き合わせは未検証（U-1） |
| P-56 | フィルタの「等しい」（FR-SRT-03） | 大文字と小文字を区別しない | Googleスプレッドシートの比較の規則に合わせた。未検証（U-1） |

| P-61 | 参照先への移動の操作（FR-REF-01） | Ctrl+クリックと右クリックメニュー | Googleスプレッドシートでは Ctrl+クリックは離れた複数の範囲の選択（FR-SEL-06、将来）にあたる。FR-SEL-06 を作るときに割り当てを見直す |
| P-62 | CSV の出力の書き方（FR-OUT-01） | UTF-8（BOM なし）・LF・末尾の改行 1 つ。1 行目は列名。値は RFC 4180 の規則で、`,` `"` 改行を含む値と空文字列を `"` で囲む。未入力（null）は空欄、真偽値は `true` / `false`、リストは空白なしの JSON の配列（`[1,3]`、`["火","光"]`） | 差分が 1 行で出るよう、ほかの出力と同じ UTF-8・LF にした（Excel で直接開くと日本語が化ける）。リストを JSON にしたのは、要素に区切り文字を含む文字列があっても曖昧にならないため。空文字列は `default: ""` のときだけ出る（DR-15）ので、空欄の null と区別できるよう囲む |
| P-63 | Protocol Buffers の出力（FR-OUT-01） | テーブルごとに proto3 のスキーマ（`<table>.proto`）とデータ（`<table>.pb`）を出す。パッケージは `sheetcraft`、メッセージはレコードが `<Table>`（テーブル名を PascalCase に）、全体が `<Table>Table { repeated <Table> records = 1; }`。フィールド名は列名、番号は出力する列の順に 1 から。型は `int`・`int64` → `int64`、`float` → `double`、`bool` → `bool`、`string`・`enum`・`datetime` → `string`、リスト型 → `repeated`（数値は packed）。スカラーは `optional` にして、未入力（null）はフィールドを書かない。メッセージ名（`foo` と `foo_table` の `FooTable` など）や列の JSON 名（`a_1` と `a1` など）が重なるテーブルと、proto の識別子にならない名前（テーブル `_1` のメッセージ名 `1`、書式に合わない列名など）は、`--force` でも出力しない（画面の出力のダイアログでは「エラーがあっても出力する」を出さず、CLI は `--force` でも出力できない旨を示す）。表示名はコメントに入れる（改行と NUL は空白にする） | `int` は ±2^53−1 まで（DR-36）で `int32` に収まらない。列挙型の値は番号を持たず、`火` のように proto の識別子にできない値もあるので、文字列にした。符号化は依存を増やさず自前で行い、フィールドの並びを番号順に固定する（FR-OUT-03）。名前の重なりは protoc がエラーにする。制約: 列の並べ替え・削除でフィールド番号が変わるので、古い `.proto` から作ったコードで新しい `.pb` は読めない（`.proto` と `.pb` は常に一緒に更新する前提）。リストの null と空のリストは区別できない。`.proto` と `.pb` の検証は protoc（grpcio-tools 1.84.0 に同梱の libprotoc 35.1）と Python の protobuf 7.36.1 で行い、手元でのみ確認（CI では行わない） |
| P-64 | 版を指定した出力（FR-OUT-07） | 列名が `version` の列で絞り込む（P-57 と同じく列名で判定する。`version` 列の無いテーブルはすべて出す）。比べ方は semver 2.0.0 の優先順位（`0.1.2` < `0.1.11`、`1.0.0-rc.1` < `1.0.0`、ビルドメタデータは無視）。`version` が未入力（空文字を含む）のレコードは常に出す。semver として読めない `version`（`0.1` など）はエラーにし、そのレコードは出さない（`--force` でも出さない）。指定した版そのものが読めなければ、CLI は使い方の誤り（終了コード 2）、画面は入力欄でエラーを示して出力できなくする。絞り込んだレコードだけのプロジェクトの写しで計算と検査をやり直すので、残したレコードが除いたレコードを `ref` や `REF()` で参照していればエラーになる（`--force` なら出力する。その値は P-51 のとおり） | 主キーを (id, version) の組にして版ごとに値を変える方式は、主キーで照合する REF・ref・`unique`・採番・診断（FR-VAL-08）をすべて変えることになるので採らなかった（2026-10-15 に利用者が決定。版ごとの値の違いはブランチで管理する）。空の `version` を常に出すのは、サンプルの `character` のように最初からあるレコードに版を書かない使い方に合わせたため。参照切れをエラーにするのは、ゲーム側で参照先が見つからないデータを出さないため（2026-10-15 に利用者が決定） |
