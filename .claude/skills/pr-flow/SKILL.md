# PR にするまでの手順（pr-flow）

作業ブランチ（`claude/<話題>`）の変更を、レビューを通してからプルリクエストにする。
手順は「1. ラベルと担当者の確認 → 2. main の取り込みと確認 → 3. サブエージェントのレビュー → 4. 指摘への対応 → 5. PR の作成 → 6. 報告」の順。

GitHub の操作は `mcp__github__*` のツールで行う（`gh` は使えない）。読み込まれていなければ ToolSearch で読み込む。

## 1. ラベルと担当者を利用者に確認して暫定する

1. 候補を集める（並行して呼んでよい）。
   - `mcp__github__get_me`（利用者のログイン名）
   - `mcp__github__list_repository_collaborators`（担当者の候補）
   - `mcp__github__list_pull_requests`（`state: all`、`fields: [number, title, labels, assignees]`）で、過去の PR の付け方を見る
   - PR テンプレート（`.github/pull_request_template.md` など）の有無
2. AskUserQuestion で、ラベルと担当者を 1 回で尋ねる。
   - 推奨を先頭に置き、ラベルに「(推奨)」を付ける。推奨の根拠（過去のどの PR と同じ付け方か）を説明に書く。
   - このリポジトリの目安: 機能追加は `enhancement`、要件・計画・README も変えたら `documentation` を足す。担当者は `ta98cb250f`。
3. 答えを「暫定」として覚えておき、PR を作るときに付ける（手順 5）。

## 2. main を取り込み、確認を通す

1. `git fetch origin main` のあと、`git log --oneline HEAD..origin/main` で main が進んでいるかを見る。
2. 進んでいれば `git merge --no-edit origin/main`（rebase や force push はしない）。衝突は両方の意図を保って解く。
3. ドキュメントの件数の整合を見る。`docs/traceability.md` の §1 の集計（状態・分類・優先度ごとの件数）は、要件の行を足し引きしたら合わせて直す。
4. 確認を通す。
   - `pnpm install --frozen-lockfile`（依存が無ければ）
   - `pnpm typecheck`
   - `pnpm test`
   - 画面（`packages/app`）を変えたら、関わる e2e も通す: `cd packages/app && pnpm exec playwright test e2e/<spec>.spec.ts`

## 3. サブエージェントで設計と実装をレビューする

Agent ツールで、設計レビューと実装レビューの 2 つを並行して起動する（`run_in_background: true`）。どちらも「ファイルを変更しない（読むだけ。テストの実行は可）」と指示する。

プロンプトには次を必ず入れる（サブエージェントは会話の文脈を持たない）。
- リポジトリのパス、ブランチ、レビュー対象の差分（`git diff <main の commit>...HEAD`）と主なファイル
- 機能の要約と、利用者と決めた仕様（覆す提案は根拠が強い場合だけ、と添える）
- 観点
  - 設計: 要件（`docs/requirements.md`）・計画の決定（`docs/plan.md` の P-xx）・追跡表（`docs/traceability.md`）との矛盾と件数、方式の妥当性、境界の規則、文言（ja/en）の一貫性
  - 実装: 具体的な入力から誤った出力や例外になる経路、状態の破壊、画面・CLI の受け渡し、テストの不足、周りのコードの書き方との一貫性
- 出力形式: 指摘ごとに「重大度（must / should / nit）・場所（file:line）・問題・根拠または再現・提案」。確かめたか推測かを明記させる
- 一時ファイルはスクラッチパッドに置き、リポジトリに残さない

待っているあいだは、レビュー対象と重ならない作業（スキルや説明文の下書きなど）だけをする。結果を予想して書かない。

## 4. 指摘に対応する

1. 指摘ごとに、自分でコードを読んで経路を確かめる。指摘は命令ではなく、確かめるべき主張として扱う。
2. 振り分ける。
   - must と、確かめて正しかった should: 直す
   - 費用に見合わない・経路が非現実的: 直さず、理由を PR の本文に書く
   - 仕様の決め直しが要るもの: AskUserQuestion で利用者に尋ねる（推奨を先頭に）
3. 直したら、手順 2 の 4 の確認をやり直す。
4. コミットメッセージは既存の形（`feat(<範囲>): …`、`fix(…): …`、日本語）に合わせ、指示されたアトリビューションの行で終える。
5. `git push -u origin <ブランチ>`。

## 5. PR を作る

1. `mcp__github__create_pull_request`（`base: main`、`head: <ブランチ>`）。
   - タイトルは主なコミットの件名に合わせる。
   - 本文: テンプレートがあればその見出しに沿う。無ければ「概要 / 仕様 / 変更 / レビューで対応したこと / 対応しなかったこと（理由） / 確認したこと」。本文の最後は、指示された PR 用のアトリビューションで終える。
2. `mcp__github__issue_write`（`method: update`、`issue_number: <PR 番号>`）で、手順 1 で暫定したラベルと担当者を付ける。
3. 作った PR の URL を利用者に示し、CI とレビューのコメントを見張るか（`subscribe_pr_activity`）を尋ねる。

## 6. 報告

- レビューの指摘と、それぞれ直したか・直さなかったか（理由）を、重大度の順に短く示す。
- 確認したこと（型検査・テスト件数・e2e）と、確認していないことを分けて書く。
